## 3. Теория

### 3.1. Что такое файл, проецируемый в память (MMF)

**Memory-Mapped File (MMF)** — механизм Windows, который позволяет «отобразить» содержимое файла
на участок (регион) виртуального адресного пространства процесса. После этого с файлом
работают как с обычной памятью: читают и пишут по указателю, без вызовов `ReadFile`/`WriteFile`.

Сравнение с виртуальной памятью:

* **Виртуальная память** (`VirtualAlloc`) — резервируется регион адресного пространства, и ему
  передаётся физическая память **из системного страничного файла** (pagefile.sys).
* **Проецируемый файл** — тоже резервируется регион, но физическая память берётся
  **из файла на диске** (exe, dll, файл данных). Как только файл спроецирован, к нему можно
  обращаться так, будто он целиком загружен в память. Система сама подгружает нужные страницы
  при обращении к ним.

### 3.2. Где применяются MMF

1. **Загрузка EXE и DLL.** Windows не копирует exe/dll в память целиком, а проецирует их.
   Экономится место в страничном файле и время запуска программы.
2. **Доступ к файлам данных на диске.** Можно работать с файлом как с массивом в памяти, без
   операций ввода/вывода и ручной буферизации.
3. **Обмен данными между процессами** на одном компьютере. Это и есть тема лабы.
   Каждый процесс имеет своё изолированное адресное пространство, и просто передать указатель
   другому процессу нельзя. Но если два процесса спроецируют **один и тот же** объект
   «проецируемый файл», они будут видеть **одни и те же физические страницы памяти**:
   один записал — другой сразу прочитал.

> Важно: для обмена данными между процессами не обязательно иметь настоящий файл на диске.
> Если в `CreateFileMapping` вместо описателя файла передать `INVALID_HANDLE_VALUE`
> (в Delphi `$FFFFFFFF`, в C# `new IntPtr(-1)`), то проекция создаётся **в системном страничном
> файле**. Это просто кусок общей памяти с именем. Именно так сделано в лабе.

### 3.3. Объекты ядра и описатели (handle)

`CreateFile`, `CreateFileMapping`, `OpenFileMapping` создают/открывают **объекты ядра** — структуры,
которые живут в памяти ядра Windows. Программа напрямую к ним доступа не имеет, она получает
**описатель (handle)** — число, по которому система находит объект.

* Описатель **зависит от процесса**: в двух процессах один и тот же объект может иметь разные
  числовые описатели.
* У каждого объекта ядра есть **счётчик пользователей**. Каждый `Create...`/`Open...` увеличивает
  его, каждый `CloseHandle` уменьшает. Когда счётчик становится 0 — **объект уничтожается**.
  Для нашего MMF это значит, что данные пропадают, когда все процессы закрыли свои описатели.

### 3.4. Порядок работы с MMF

Подготовка (3 шага):

1. Создать или открыть объект ядра **«файл»** — функция `CreateFile`.
   *(В лабе пропускаем: вместо файла используем страничный файл, `INVALID_HANDLE_VALUE`.)*
2. Создать объект ядра **«проецируемый файл»** — `CreateFileMapping`. Здесь сообщаем системе
   размер и способ доступа.
3. Спроецировать этот объект (целиком или частично) на адресное пространство процесса —
   `MapViewOfFile`. Получаем указатель на память.

Завершение (3 шага, в обратном порядке):

1. Отменить проецирование — `UnmapViewOfFile`.
2. Закрыть объект «проецируемый файл» — `CloseHandle`.
3. Закрыть объект «файл» — `CloseHandle`. *(В лабе не нужно, файла нет.)*

### 3.5. Функция `CreateFile`

```c
HANDLE CreateFile(
    LPCTSTR lpFileName,                    // имя файла (с путём)
    DWORD dwDesiredAccess,                 // доступ: 0, GENERIC_READ, GENERIC_WRITE
    DWORD dwShareMode,                     // совместный доступ: 0, FILE_SHARE_READ, FILE_SHARE_WRITE
    LPSECURITY_ATTRIBUTES lpSecurityAttributes,
    DWORD dwCreationDistribution,          // создать / открыть существующий и т.п.
    DWORD dwFlagsAndAttributes,
    HANDLE hTemplateFile);
```

* `lpFileName` — имя файла.
* `dwDesiredAccess` — что можно делать с содержимым:
  * `0` — ни читать, ни писать, только получить атрибуты;
  * `GENERIC_READ` — чтение;
  * `GENERIC_WRITE` — запись (можно комбинировать `GENERIC_READ | GENERIC_WRITE`).
* `dwShareMode` — может ли другой процесс открыть файл одновременно с нами:
  * `0` — нельзя никак;
  * `FILE_SHARE_READ` — другим можно только читать (открыть с `GENERIC_WRITE` не получится);
  * `FILE_SHARE_WRITE` — другим можно только писать (открыть с `GENERIC_READ` не получится).
* Возвращает описатель файла, а при ошибке — `INVALID_HANDLE_VALUE`
  (**не ноль!**, это частая ловушка).

### 3.6. Функция `CreateFileMapping`

```c
HANDLE CreateFileMapping(
    HANDLE hFile,                          // описатель файла или INVALID_HANDLE_VALUE
    LPSECURITY_ATTRIBUTES lpFileMappingAttributes, // обычно NULL (в Delphi nil)
    DWORD flProtect,                       // защита страниц
    DWORD dwMaximumSizeHigh,               // размер, старшие 32 бита
    DWORD dwMaximumSizeLow,                // размер, младшие 32 бита
    LPCTSTR lpName);                       // имя объекта
```

* `hFile` — какой файл проецировать. `INVALID_HANDLE_VALUE` → страничный файл.
* `lpFileMappingAttributes` — атрибуты безопасности, обычно `NULL`.
* `flProtect` — атрибут защиты страниц физической памяти (сама функция память ещё не выделяет,
  но запоминает, какую защиту ставить потом):
  * `PAGE_READONLY` — только чтение;
  * `PAGE_READWRITE` — чтение и запись;
  * `PAGE_WRITECOPY` — чтение и запись, но запись создаёт **закрытую копию страницы**
    (копирование при записи — изменения видит только этот процесс, в файл они не попадают).
* `dwMaximumSizeHigh` / `dwMaximumSizeLow` — максимальный размер в байтах. Размер 64-битный, поэтому
  разбит на две 32-битные половины. Если передать `0, 0` — размер будет равен текущему размеру
  файла (для страничного файла так нельзя, нужно указать размер явно — у нас `0, 1024`).
* `lpName` — имя объекта. **По этому имени второй процесс найдёт объект.** У нас `"MMFSharedData"`.

**Как работает функция:**

* Если объекта с таким именем **нет** — создаёт его и возвращает описатель.
* Если объект с таким именем **уже есть** — новый не создаёт, увеличивает счётчик пользователей
  существующего и возвращает описатель на него. Размер при этом **не меняется**.
  `GetLastError()` в этом случае вернёт `ERROR_ALREADY_EXISTS` (183). То есть функция
  **выполнилась успешно**, просто объект не новый.
* При ошибке возвращает `NULL` (0).

Именно проверка `GetLastError() == ERROR_ALREADY_EXISTS` позволяет понять, мы создали объект
или подключились к чужому.

### 3.7. Функция `OpenFileMapping`

```c
HANDLE OpenFileMapping(
    DWORD dwDesiredAccess,   // FILE_MAP_READ, FILE_MAP_WRITE, FILE_MAP_ALL_ACCESS, FILE_MAP_COPY
    BOOL bInheritHandle,     // наследуют ли дочерние процессы этот описатель
    LPCTSTR lpName);         // имя объекта
```

* Похожа на `CreateFileMapping`, но **только открывает существующий** объект. Если объекта
  с таким именем нет — **ничего не создаёт** и возвращает `NULL` (0).
* Схема: первый процесс создаёт объект `CreateFileMapping`, второй открывает его
  `OpenFileMapping` по тому же имени.
* `bInheritHandle` — если `TRUE`, дочерние процессы (запущенные этим процессом) получат
  копию описателя. У нас `false`.
* Возвращает «процессозависимый» описатель объекта, созданного первым процессом.

### 3.8. Функция `MapViewOfFile`

```c
LPVOID MapViewOfFile(
    HANDLE hFileMappingObject,   // описатель из CreateFileMapping / OpenFileMapping
    DWORD dwDesiredAccess,       // вид доступа
    DWORD dwFileOffsetHigh,      // смещение начала окна, старшие 32 бита
    DWORD dwFileOffsetLow,       // смещение начала окна, младшие 32 бита
    SIZE_T dwNumberOfBytesToMap);// размер окна в байтах (0 = до конца)
```

Создание объекта «проецируемый файл» само по себе память процессу не даёт. Нужно попросить
систему зарезервировать регион в адресном пространстве процесса и связать его с данными
объекта — это и делает `MapViewOfFile`. Возвращает **указатель** на начало региона
(или `NULL` при ошибке).

`dwDesiredAccess`:

* `FILE_MAP_WRITE` — чтение и запись (объект должен быть создан с `PAGE_READWRITE`);
* `FILE_MAP_READ` — только чтение (`PAGE_READONLY`, `PAGE_READWRITE` или `PAGE_WRITECOPY`);
* `FILE_MAP_ALL_ACCESS` — то же, что `FILE_MAP_WRITE` (полный доступ);
* `FILE_MAP_COPY` — чтение и запись с копированием при записи (закрытая копия страницы).

**Оконное представление (view).** Не обязательно проецировать весь файл. Можно спроецировать
только кусок — «окно». Отсюда название функции: Map **View** Of File. Для окна задаются:

* с какого байта файла начинается окно — `dwFileOffsetHigh` + `dwFileOffsetLow`
  (смещение должно быть кратно гранулярности выделения памяти, обычно 64 КБ);
* сколько байт проецировать — `dwNumberOfBytesToMap`. `0` — до конца объекта.

У нас проецируется весь объект: `0, 0, 0`.

### 3.9. Функция `UnmapViewOfFile`

```c
BOOL UnmapViewOfFile(LPCVOID lpBaseAddress);
```

Освобождает регион адресного пространства, занятый окном. Параметр — **тот самый адрес**, который
вернула `MapViewOfFile`. Если её не вызвать, регион не освободится до завершения процесса.

Важно: `UnmapViewOfFile` **не уничтожает** объект «проецируемый файл» и данные в нём. Она только
убирает «окно» из нашего процесса. Данные живут, пока открыт хотя бы один описатель объекта.

### 3.10. Функция `CloseHandle`

```c
BOOL CloseHandle(HANDLE hObject);
```

Закрывает описатель любого объекта ядра (уменьшает счётчик пользователей). Если описатели не
закрывать, при долгой работе программы их накопится много (утечка ресурсов). При завершении
процесса система сама закроет всё, что осталось открытым.

Для полного завершения работы с MMF на диске `CloseHandle` вызывается **дважды**: для объекта
«проецируемый файл» и для объекта «файл». У нас объекта «файл» нет, поэтому один раз.

### 3.11. Как идёт обмен данными в нашей программе (схема)

```
 Процесс A (первая копия)                       Процесс B (вторая копия)
 ------------------------                       ------------------------
 CreateFileMapping("MMFSharedData")  ──┐
   → объект создан, счётчик = 1        │
 MapViewOfFile → указатель pA          │
 копируем текст по адресу pA ───────►  [ общая физическая память, 1024 байта ]
 UnmapViewOfFile(pA)                   │             ▲
 (hMapping остаётся открыт,            │             │
  объект живёт)                        │   OpenFileMapping("MMFSharedData")
                                       │     → счётчик = 2
                                       │   MapViewOfFile → указатель pB
                                       │   читаем текст по адресу pB ──┘
                                       │   UnmapViewOfFile(pB)
                                       │   CloseHandle → счётчик = 1
 [Close mapping] CloseHandle(hMapping) ┘
   → счётчик = 0, объект уничтожен
```

Указатели `pA` и `pB` — разные числа (у каждого процесса своё адресное пространство), но
указывают они на **одни и те же физические страницы**.

## 4. Как C# вызывает функции WinAPI (P/Invoke)

В C# нет готовых функций `CreateFileMapping` и т.п. — это функции из системной библиотеки
`kernel32.dll`, написанные на C. Чтобы вызвать их из C#, используется механизм
**P/Invoke** (Platform Invoke): мы описываем заголовок функции с атрибутом `[DllImport]`,
а .NET сам находит её в DLL и вызывает.

```csharp
[DllImport("kernel32.dll", SetLastError = true, CharSet = CharSet.Unicode)]
static extern IntPtr CreateFileMapping(IntPtr hFile, IntPtr lpFileMappingAttributes,
    uint flProtect, uint dwMaximumSizeHigh, uint dwMaximumSizeLow, string lpName);
```

* `DllImport("kernel32.dll")` — в какой DLL лежит функция.
* `static extern` — тело функции не в нашем коде, а снаружи.
* `SetLastError = true` — .NET сохраняет код ошибки сразу после вызова, чтобы его можно было
  получить через `Marshal.GetLastWin32Error()` (это аналог `GetLastError()` из Delphi/C).
* `CharSet = CharSet.Unicode` — строки передаются в Unicode (вызывается `CreateFileMappingW`).

Соответствие типов:

| WinAPI (C)         | Delphi      | C#        | Пояснение                               |
|--------------------|-------------|-----------|-----------------------------------------|
| `HANDLE`           | `THandle`   | `IntPtr`  | описатель, размер = размер указателя    |
| `LPVOID`           | `Pointer`   | `IntPtr`  | указатель на память                     |
| `DWORD`            | `DWORD`     | `uint`    | 32-битное беззнаковое                   |
| `SIZE_T`           | `SIZE_T`    | `UIntPtr` | беззнаковое размером с указатель        |
| `BOOL`             | `BOOL`      | `bool`    |                                         |
| `LPCTSTR`          | `PChar`     | `string`  | строка с нулём в конце                  |
| `NULL`             | `nil` / `0` | `IntPtr.Zero` |                                     |

Значения констант взяты из заголовочных файлов Windows (`winnt.h`, `winbase.h`, `winerror.h`):

| Константа              | Значение     |
|------------------------|--------------|
| `PAGE_READWRITE`       | `0x04`       |
| `FILE_MAP_ALL_ACCESS`  | `0xF001F`    |
| `ERROR_ALREADY_EXISTS` | `183`        |
| `INVALID_HANDLE_VALUE` | `-1` (`$FFFFFFFF` в 32-битном Delphi) |

**Работа с памятью по указателю.** В C# нельзя просто так написать `StrPCopy(PMapData, s)` как в
Delphi. Для этого есть класс `Marshal`:

* `Marshal.Copy(массив_байт, 0, указатель, длина)` — скопировать байты из массива C# в
  неуправляемую память по указателю (запись в MMF);
* `Marshal.PtrToStringUni(указатель)` — прочитать Unicode-строку из памяти до нулевого символа
  (чтение из MMF).

### Задание 1 (п. 1). Две копии программы, каждая в своём окне

```csharp
[STAThread]
static void Main()
{
    Application.EnableVisualStyles();
    Application.SetCompatibleTextRenderingDefault(false);
    Application.Run(new Form1());
}
```

Каждый запуск `MmfLab.exe` — отдельный процесс со своим окном. Чтобы на скриншотах было видно,
что процессы разные, в конструкторе формы в заголовок окна выводится ID процесса:

```csharp
Text = "MMF - процесс " + System.Diagnostics.Process.GetCurrentProcess().Id;
```

### Задание 2 (пп. 2, 2.2, 2.3). Элементы формы

Описаны в `Form1.Designer.cs`. Вместо дельфийских `Edit`, `Label`, `BitBtn` в WinForms используются
`TextBox`, `Label`, `Button`:

| Элемент Delphi | Элемент C#  | Имя в коде  | Текст                         | Назначение                     |
|----------------|-------------|-------------|-------------------------------|--------------------------------|
| `Label`        | `Label`     | `lblData`   | `Data`                        | подпись к полю                 |
| `Edit`         | `TextBox`   | `editData`  | —                             | ввод / вывод передаваемых данных |
| `BitBtn1`      | `Button`    | `btnCreate` | `Create mapping of Data`      | создать проекцию               |
| `BitBtn3`      | `Button`    | `btnOpen`   | `Open mapping and get Data`   | открыть проекцию и получить данные |
| `BitBtn2`      | `Button`    | `btnClose`  | `Close mapping of Data`       | закрыть проекцию (при запуске недоступна) |
| `BitBtn4`      | `Button`    | `btnExit`   | `Exit`                        | выход                          |

Кнопка `btnClose` при запуске недоступна: в дизайнере у неё `Enabled = false`.
В Delphi-примере кнопки прятались через `Visible`, здесь используется `Enabled` (кнопка видна,
но серая) — так нагляднее, суть та же.

Ограничение длины текста задаётся в конструкторе:

```csharp
editData.MaxLength = 500;
```

Зачем: размер проекции 1024 байта, строка хранится в Unicode (2 байта на символ) плюс 2 байта на
завершающий ноль. 500 × 2 + 2 = 1002 < 1024 — гарантированно влезает, выхода за границу памяти
не будет.

### Объявления в начале `Form1.cs`

```csharp
static readonly IntPtr INVALID_HANDLE_VALUE = new IntPtr(-1);
const uint PAGE_READWRITE = 0x04;
const uint FILE_MAP_ALL_ACCESS = 0xF001F;
const int ERROR_ALREADY_EXISTS = 183;

const string MAPPING_NAME = "MMFSharedData"; // имя объекта
const int MAPFILESIZE = 1024;                // размер в байтах
```

Дальше идут `[DllImport]`-объявления пяти функций WinAPI (см. раздел 4) и поле формы:

```csharp
IntPtr hMapping = IntPtr.Zero;
```

`hMapping` — описатель созданного нами объекта. Он хранится в поле формы (а не в локальной
переменной), потому что нужен и кнопке «Создать», и кнопке «Закрыть». Пока он открыт —
объект с данными существует в системе.

### Задание п. 2.4. Кнопка «Create mapping of Data» — `btnCreate_Click`

**Шаг 1. Создаём объект «проецируемый файл»:**

```csharp
hMapping = CreateFileMapping(INVALID_HANDLE_VALUE, IntPtr.Zero,
    PAGE_READWRITE, 0, MAPFILESIZE, MAPPING_NAME);

bool isNew = Marshal.GetLastWin32Error() != ERROR_ALREADY_EXISTS;
```

* `INVALID_HANDLE_VALUE` — файла на диске нет, используем страничный файл;
* `IntPtr.Zero` — атрибуты безопасности по умолчанию (`nil`);
* `PAGE_READWRITE` — можно читать и писать;
* `0, MAPFILESIZE` — размер 1024 байта (старшая часть 0, младшая 1024);
* `MAPPING_NAME` — имя `"MMFSharedData"`.

Сразу после вызова читаем код ошибки. Если он равен `ERROR_ALREADY_EXISTS` — объект с таким
именем уже был создан другой копией программы, и мы получили описатель на чужой объект.
Читать код ошибки нужно **сразу**, пока его не затёр какой-нибудь другой вызов.

**Шаг 2. Проверка, что объект создан:**

```csharp
if (hMapping == IntPtr.Zero)
{
    MessageBox.Show("Can't create file mapping", ...);
    Application.Exit();
    return;
}
```

`CreateFileMapping` при ошибке возвращает 0. Как и в методичке — сообщение и завершение программы.

**Шаг 3. Проецируем объект на адресное пространство процесса:**

```csharp
IntPtr pMapData = MapViewOfFile(hMapping, FILE_MAP_ALL_ACCESS, 0, 0, UIntPtr.Zero);

if (pMapData == IntPtr.Zero)
{
    CloseHandle(hMapping);
    hMapping = IntPtr.Zero;
    MessageBox.Show("Can't view memory map", ...);
    Application.Exit();
    return;
}
```

`0, 0` — окно с начала объекта, `UIntPtr.Zero` — на весь размер. Получаем указатель `pMapData`
на общую память. Если не получилось — закрываем описатель (чтобы не было утечки) и выходим.

**Шаг 4а. Объект новый — пишем в него данные:**

```csharp
if (isNew)
{
    byte[] bytes = Encoding.Unicode.GetBytes(editData.Text + "\0");
    Marshal.Copy(bytes, 0, pMapData, bytes.Length);

    UnmapViewOfFile(pMapData);

    btnCreate.Enabled = false;
    btnClose.Enabled = true;
    editData.Text = "";
}
```

* `Encoding.Unicode.GetBytes(...)` — переводим строку в массив байт (UTF-16, по 2 байта на символ).
  Добавляем `"\0"` — нулевой символ в конце, чтобы читающая сторона знала, где строка кончается
  (это аналог `StrPCopy`, который тоже пишет строку с нулём в конце).
* `Marshal.Copy` — копируем байты в общую память по адресу `pMapData`.
* `UnmapViewOfFile(pMapData)` — окно больше не нужно, убираем его. **Объект при этом не
  удаляется**, потому что `hMapping` остаётся открытым, — данные продолжают жить в системе.
* Блокируем кнопку «Create» (второй раз создать нельзя) и разблокируем «Close».
* Очищаем поле ввода — чтобы потом было видно, что данные реально приходят из памяти,
  а не остались в поле.

**Шаг 4б. Объект уже существует — выводим сообщение (рис. 7.1):**

```csharp
else
{
    UnmapViewOfFile(pMapData);
    CloseHandle(hMapping);
    hMapping = IntPtr.Zero;

    MessageBox.Show("Mapping Already Exists", ...);
}
```

Это ситуация, когда первая копия уже создала проекцию, а во второй тоже нажали «Create».
`CreateFileMapping` при этом вернул описатель на **существующий** объект, поэтому мы аккуратно
отключаем окно и закрываем описатель (в Delphi-примере этого не было — описатель утекал),
после чего показываем сообщение **«Mapping Already Exists»**. Данные в объекте не трогаем.

### Задание п. 2.5. Кнопка «Open mapping and get Data» — `btnOpen_Click`

**Шаг 1. Открываем существующий объект по имени:**

```csharp
IntPtr opMapping = OpenFileMapping(FILE_MAP_ALL_ACCESS, false, MAPPING_NAME);

if (opMapping == IntPtr.Zero)
{
    MessageBox.Show("Can't Open Mapping", ...);
    Application.Exit();
    return;
}
```

* `FILE_MAP_ALL_ACCESS` — полный доступ;
* `false` — дочерние процессы описатель не наследуют;
* `MAPPING_NAME` — то же имя `"MMFSharedData"`, что и при создании.

Если объекта нет (никто не нажал «Create», или проекцию уже закрыли) — функция вернёт 0.
**По заданию** в этом случае выводится сообщение **«Can't Open Mapping»** и программа завершается.

**Шаг 2. Проецируем на своё адресное пространство:**

```csharp
IntPtr pMapData = MapViewOfFile(opMapping, FILE_MAP_ALL_ACCESS, 0, 0, UIntPtr.Zero);

if (pMapData == IntPtr.Zero)
{
    CloseHandle(opMapping);
    MessageBox.Show("Can't map view", ...);
    Application.Exit();
    return;
}
```

Точно так же, как при создании. Указатель в этом процессе будет другим числом, но указывает на
те же физические страницы.

**Шаг 3. Читаем данные и выводим в поле:**

```csharp
editData.Text = Marshal.PtrToStringUni(pMapData);
```

`PtrToStringUni` читает Unicode-символы, начиная с адреса `pMapData`, пока не встретит нулевой
символ, и собирает из них строку C#. Аналог дельфийского `string(pchar(PMapData))`.

**Шаг 4. Освобождаем ресурсы:**

```csharp
UnmapViewOfFile(pMapData);
CloseHandle(opMapping);
```

Сначала убираем окно, потом закрываем свой описатель (счётчик пользователей объекта уменьшается
на 1). Объект при этом не исчезает, потому что первая копия программы всё ещё держит `hMapping`.

### Задание п. 2.6. Кнопка «Close mapping of Data» — `btnClose_Click`

```csharp
private void btnClose_Click(object sender, EventArgs e)
{
    if (hMapping != IntPtr.Zero)
    {
        CloseHandle(hMapping);
        hMapping = IntPtr.Zero;
    }

    btnClose.Enabled = false;
    btnCreate.Enabled = true;
}
```

* Закрываем описатель объекта. Если больше никто этот объект не держит (а вторая копия закрывает
  свой описатель сразу после чтения), счётчик становится 0 и **объект уничтожается**, память
  в страничном файле освобождается.
* Обнуляем `hMapping`, чтобы случайно не закрыть его второй раз.
* Кнопка «Close» снова недоступна, «Create» — доступна.

### Задание п. 2.7. Кнопка «Exit» — `btnExit_Click`

```csharp
private void btnExit_Click(object sender, EventArgs e)
{
    Close();
}
```

`Close()` закрывает форму, а так как это главная форма — завершается и программа (аналог `close`
в Delphi).

Дополнительно добавлен обработчик закрытия формы — он срабатывает при любом закрытии окна
(кнопкой Exit, крестиком, Alt+F4) и закрывает описатель, если его забыли закрыть кнопкой:

```csharp
private void Form1_FormClosing(object sender, FormClosingEventArgs e)
{
    if (hMapping != IntPtr.Zero)
    {
        CloseHandle(hMapping);
        hMapping = IntPtr.Zero;
    }
}
```

(Система и так закрыла бы его при завершении процесса, но правильно закрывать самому.)

## 8. Возможные вопросы на защите

**Что такое MMF?** Механизм, при котором содержимое файла отображается на регион адресного
пространства процесса, и с файлом работают как с обычной памятью.

**Чем отличается от виртуальной памяти?** При `VirtualAlloc` физическая память берётся из
страничного файла, а при MMF — из указанного файла на диске (или тоже из страничного, если
передать `INVALID_HANDLE_VALUE`, как у нас).

**Где лежат наши данные?** В страничном файле системы (и в оперативной памяти), т.к. вместо
файла передан `INVALID_HANDLE_VALUE`. Файла на диске нет.

**Как второй процесс находит данные первого?** По **имени** объекта ядра — `"MMFSharedData"`.
Первый создаёт объект с этим именем через `CreateFileMapping`, второй открывает его через
`OpenFileMapping`.

**Почему адреса (указатели) в двух процессах разные, а данные одинаковые?** У каждого процесса своё
виртуальное адресное пространство, поэтому регион может оказаться по разным адресам. Но оба
региона отображены на одни и те же физические страницы памяти.

**Как узнать, что объект уже существует?** `CreateFileMapping` вернёт описатель, а
`GetLastError()` — `ERROR_ALREADY_EXISTS`.

**Чем `CreateFileMapping` отличается от `OpenFileMapping`?** Первая создаёт объект, а если он уже
есть — открывает существующий. Вторая только открывает существующий, а если его нет — возвращает
0 (ничего не создаёт).

**Зачем `MapViewOfFile`, если объект уже создан?** Объект ядра сам по себе — просто описание. Чтобы
получить доступ к данным по указателю, нужно спроецировать его (или его часть — «окно», view)
на адресное пространство процесса.

**Что такое view (оконное представление)?** Часть объекта «проецируемый файл», которая
спроецирована в память. Задаётся смещением (`dwFileOffsetHigh/Low`) и размером
(`dwNumberOfBytesToMap`).

**Почему после записи вызывается `UnmapViewOfFile`, а данные не пропадают?** `UnmapViewOfFile`
убирает только окно из адресного пространства процесса. Сам объект живёт, пока открыт хотя бы
один его описатель (`hMapping`).

**Когда данные пропадают?** Когда закрыты все описатели объекта (счётчик пользователей стал 0):
то есть после нажатия «Close mapping of Data» (или закрытия первой программы), при условии, что
вторая копия свой описатель уже закрыла.

**Зачем два параметра размера (`High` и `Low`)?** Размер 64-битный, а `DWORD` — 32 бита, поэтому
размер передаётся двумя половинами. У нас размер маленький, старшая часть = 0.

**Что такое `PAGE_WRITECOPY` / `FILE_MAP_COPY`?** Копирование при записи: при попытке записи
система создаёт закрытую копию страницы для этого процесса; изменения не видят другие процессы
и они не попадают в файл.

**Зачем `CloseHandle`?** Закрыть описатель объекта ядра. Иначе — утечка ресурсов (описателей),
а объект не будет уничтожен, пока процесс не завершится.

**Что такое P/Invoke и `DllImport`?** Механизм .NET для вызова функций из обычных (неуправляемых)
DLL, например `kernel32.dll`. Мы описываем заголовок функции, .NET сам её находит и вызывает.

**Зачем `SetLastError = true`?** Чтобы .NET сохранил код ошибки WinAPI сразу после вызова,
иначе его может перезаписать сама среда .NET. Получаем его через `Marshal.GetLastWin32Error()`.

**Зачем `"\0"` в конце строки?** Читающая сторона (`PtrToStringUni`) не знает длину строки и
читает до нулевого символа. Без нуля она прочитала бы мусор после строки.

**Почему `MaxLength = 500`?** Проекция 1024 байта, символ в Unicode занимает 2 байта, плюс 2 байта
на ноль: 500·2 + 2 = 1002 ≤ 1024. Так текст гарантированно помещается.

**Есть ли в .NET готовый класс для этого?** Да, `System.IO.MemoryMappedFiles.MemoryMappedFile`
(`CreateNew`, `OpenExisting`, `CreateViewAccessor`) — внутри он вызывает те же самые
`CreateFileMapping` / `OpenFileMapping` / `MapViewOfFile`. В лабе использованы функции WinAPI
напрямую, чтобы код совпадал с теорией из методички.
